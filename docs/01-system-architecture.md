# البنية المعمارية للنظام

## البنية العامة للنظام

النظام مبني على بنية **Client-Server** (عميل–خادم):

```
┌─────────────────┐         ┌─────────────────┐         ┌─────────────────┐
│   المتصفح       │   HTTP  │   Backend       │   SQL   │   قاعدة         │
│   (Frontend)    │ ──────► │   (Laravel)     │ ──────► │   البيانات      │
│   React + Vite  │   API   │   PHP + API     │         │   MySQL         │
└─────────────────┘         └─────────────────┘         └─────────────────┘
        │                            │
        │  يستدعي                    │  يقرأ/يكتب
        │  /api/...                  │  الجداول
```

- **Frontend**: يعمل في المتصفح، يقدم الواجهة ويرسل طلبات HTTP إلى الـ API.
- **Backend**: يعمل على الخادم، يستقبل الطلبات، يتحقق من الهوية والصلاحيات، ثم يقرأ أو يكتب في قاعدة البيانات.
- **قاعدة البيانات**: تخزن المستخدمين، المشاريع، المقترحات، الطلبات، الإشعارات، وغيرها.

---

## العلاقة بين Frontend و Backend وقاعدة البيانات

### 1. الواجهة الأمامية (Frontend)

- مجلد: `frontend/`
- دورها: عرض الواجهة، إرسال طلبات API، عرض الاستجابات، حفظ التوكن في المتصفح.
- لا تتصل بقاعدة البيانات مباشرة، بل فقط مع الـ Backend عبر الـ API.

### 2. الواجهة الخلفية (Backend)

- مجلد: `backend/`
- دورها: استقبال الطلبات، التحقق من المصادقة والصلاحيات، تنفيذ المنطق، قراءة/كتابة قاعدة البيانات، إرجاع JSON.

### 3. قاعدة البيانات (Database)

- نوعها: MySQL (حسب إعدادات `.env` في الـ Backend).
- دورها: تخزين جميع البيانات بشكل دائم.
- يتصل بها الـ Backend فقط عبر Laravel (Eloquent ORM).

## تدفق البيانات (Data Flow)

### مثال 1: تسجيل الدخول

```
1. المستخدم يدخل اسم المستخدم وكلمة المرور في صفحة تسجيل الدخول
2. الواجهة الأمامية ترسل POST إلى /api/auth/login مع البيانات
3. الـ Backend يتحقق من البيانات، يطابق كلمة المرور، وينشئ توكن (Token) عبر Sanctum
4. الـ Backend يرجع { token, user, permissions }
5. الواجهة الأمامية تحفظ التوكن في localStorage وتعيد توجيه المستخدم إلى لوحة التحكم
```

### مثال 2: عرض قائمة المقترحات (طالب)

```
1. الطالب يضغط على "مقترحاتي"
2. الواجهة ترسل GET /api/student/proposals مع رأس Authorization: Bearer <token>
3. الـ Backend يتحقق من التوكن، يفحص الدور (role:student)، ثم يستعلم من قاعدة البيانات
4. قاعدة البيانات ترجع المقترحات الخاصة بالطالب
5. الـ Backend يُشكّل الاستجابة بصيغة JSON
6. الواجهة تعرض القائمة في الجدول
```

### مثال 3: رفع مستند (مع نافذة زمنية)

```
1. الطالب يختار ملفاً ويضغط "رفع"
2. الواجهة ترسل POST /api/student/documents مع FormData
3. الـ Backend يمر عبر Middleware للتحقق من النافذة الزمنية (مثلاً chapter_submission_phase_1)
4. إذا لم تكن النافذة نشطة → يُرجع خطأ 403
5. إذا كانت نشطة → يحفظ الملف في storage ويعيد بيانات المستند
6. الواجهة تعرض رسالة نجاح وتحدّث القائمة
```

## الخدمات الخارجية المستخدمة

| الخدمة                   | الاستخدام                | ملاحظات                                                             |
| ------------------------ | ------------------------ | ------------------------------------------------------------------- |
| **البريد الإلكتروني**    | استعادة كلمة المرور      | الإعداد الافتراضي: `MAIL_MAILER=log` (يكتب في ملف بدلاً من الإرسال) |
| **نظام الملفات المحلي**  | تخزين المستندات المرفوعة | `FILESYSTEM_DISK=local` في `.env`                                   |
| **Redis**                | اختياري (Cache / Queue)  | غير مفعّل افتراضياً، يمكن تفعيله لتحسين الأداء                      |
| **Queue (قائمة انتظار)** | تنفيذ مهام في الخلفية    | الإعداد الافتراضي: `QUEUE_CONNECTION=database`                      |

لا توجد خدمات مدفوعة (Payment) أو تخزين سحابي خارجي في الإعداد الافتراضي.

## كيف يعمل النظام ككل

1. **الدخول**: المستخدم يسجل الدخول، يحصل على توكن ويُحفظ في المتصفح.
2. **كل طلب API**: الواجهة ترسل التوكن مع الطلب، والـ Backend يتحقق منه ويحدد دور المستخدم.
3. **النوافذ الزمنية**: بعض الإجراءات (تقديم مقترحات، رفع مستندات) تعمل فقط ضمن فترات محددة في قاعدة البيانات.
4. **الأدوار والصلاحيات**: كل دور له مسارات API خاصة به، ولا يستطيع الوصول لمسارات الدور الآخر.
5. **الإشعارات**: عند حدث معين، يكتب الـ Backend إشعاراً في قاعدة البيانات، والواجهة تعرضه للمستخدم.
